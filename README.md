# Корпоративный транспорт

Система управления корпоративным транспортом: приложение пассажира, приложение водителя и
административная панель с аналитикой загрузки маршрутов. Данные связаны в одну цепочку —
поездки пассажиров и отметки водителей формируют статистику, на основании которой
администратор принимает решения о маршрутах и транспорте.

Город тестовых данных — Худжанд. Интерфейс на русском языке.

## Быстрый старт

```bash
pnpm install
pnpm db:up
pnpm db:migrate
pnpm db:seed
pnpm dev
```

Приложение откроется на http://localhost:3000. База поднимается в Docker на порту **5433**
(нестандартный порт выбран, чтобы не конфликтовать с локально установленным PostgreSQL).

### Запуск целиком в Docker

Не нужен локальный Node/pnpm — только Docker.

```bash
pnpm docker:up      # собирает образ, поднимает БД, применяет миграции, запускает веб
pnpm docker:seed    # один раз — заполнить тестовыми данными
```

Приложение — на http://localhost:3000, БД проброшена на хост-порт **5433**, как и при
локальном запуске. `docker:up` можно вызывать повторно: миграции применяются автоматически
и безопасны при повторном запуске, а `docker:seed`/`docker:reset` — вручную (сид не идемпотентен).
Переменные `ROUTING_URL`, `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`
опциональны — заданы в `.env` (см. `.env.example`), `docker-compose.yml` подхватывает их
через `${VAR}`.

| Команда | Что делает |
|---------|-----------|
| `pnpm docker:up` | Собрать образ и поднять БД + веб (порт 3000) |
| `pnpm docker:down` | Остановить и удалить контейнеры |
| `pnpm docker:logs` | Логи веб-контейнера |
| `pnpm docker:migrate` | Повторно применить миграции |
| `pnpm docker:seed` | Заполнить тестовыми данными |
| `pnpm docker:reset` | Очистить базу |

### Деплой

Продакшен — Dokku, автодеплой из GitHub при пуше в `main`. Настройка сервера и секретов —
в [docs/deploy-dokku.md](docs/deploy-dokku.md).

## Структура

```
apps/web/            Next.js 16 (App Router), три зоны в одном приложении
  src/app/(passenger)  /app     — PWA пассажира, mobile-first
  src/app/(driver)     /driver  — PWA водителя, mobile-first
  src/app/(admin)      /admin   — панель администратора, desktop-first
  src/lib/             доступ к данным, авторизация, агрегация аналитики
packages/domain/     бизнес-логика без зависимости от фреймворков + тесты
packages/db/         схема Drizzle, миграции, сид
docs/01-analysis.md  согласованные требования, модель данных, решения по конфликтам
```

Бизнес-логика (поиск ближайшей остановки, расчёт времени прибытия, загрузка рейса,
статусы маршрутов, сигналы администратору) вынесена в `packages/domain` и покрыта тестами.
Это позволяет позже перенести её в отдельный backend или в нативные приложения без переписывания.

## Как считается загрузка

1. **Спрос** — число пассажиров, отметивших «поеду» на рейсе.
2. **Факт** — максимальное число людей в салоне по отметкам водителя на остановках.
3. **Загрузка рейса** = наибольшее из спроса и факта, делённое на вместимость назначенного транспорта.

Спрос может превышать вместимость — это и есть сигнал, что сотрудники не помещаются в транспорт.

Статусы маршрута (пороги настраиваются в разделе «Настройки»):

| Статус | Условие по умолчанию |
|--------|---------------------|
| Перегрузка | не менее 30% рейсов с загрузкой от 100%, либо средняя загрузка от 95% |
| Низкая загрузка | средняя загрузка ниже 40% |
| Норма | остальные случаи |

Система не изменяет маршруты автоматически. Она показывает данные и предлагает варианты;
решение принимает администратор.

## Время прибытия: три источника

Система выбирает самый точный из доступных источников:

1. **GPS** — пока телефон водителя передаёт координаты, положение проецируется на линию
   маршрута, и время считается по оставшемуся расстоянию и скорости.
2. **Отметки водителя** — если координат нет, время пересчитывается от фактической отметки
   «Прибыл» на предыдущей остановке.
3. **Расписание** — отправление плюс смещение остановки.

Клиент обновляет живые данные раз в 15 секунд и сразу при возврате на вкладку; в фоне
опрос не идёт, чтобы не расходовать батарею.

## GPS и мониторинг

Телефон водителя передаёт координаты каждые 15 секунд, **только пока рейс в пути**: отслеживание
начинается по кнопке «Начать рейс» и прекращается при его завершении.

Администратор видит раздел «Мониторинг»: транспорт на карте, состояние связи и сигналы:

| Сигнал | Когда возникает |
|--------|-----------------|
| Отклонение от маршрута | Несколько точек подряд дальше заданного расстояния от линии маршрута |
| Нет данных о транспорте | Рейс начат, но координаты не приходят дольше заданного времени |
| Рейс не начат | Время отправления прошло, а водитель не начал рейс |

Пороги настраиваются в разделе «Настройки».

## Push-уведомления

Приложение работает как PWA и умеет присылать уведомления, когда закрыто: подъезд транспорта
к вашей остановке, изменение маршрута, отмена рейса, сообщение администратора.

Пассажир и водитель включают их сами в профиле — браузер спрашивает разрешение только по нажатию
кнопки. Для работы нужны ключи VAPID в `apps/web/.env`:

```bash
node -e "console.log(require('web-push').generateVAPIDKeys())"
```

Без ключей приложение работает обычным образом, уведомления остаются только внутри приложения.
Push требует HTTPS; на `localhost` работает без сертификата.

## Версии маршрутов

Форма маршрута — порядок остановок, время в пути и геометрия — хранится не в самом маршруте,
а в его версии. Каждый рейс закреплён за версией, по которой фактически ехал.

Это нужно, чтобы изменение маршрута не переписывало прошлое. Без версий завершённый рейс
недельной давности начал бы ссылаться на новый порядок остановок, и аналитика загрузки
по остановкам показала бы то, чего не было.

| Что происходит при сохранении | Результат |
|-------------------------------|-----------|
| Изменились остановки или время | Создаётся новая версия, она становится действующей |
| Изменились только название, цвет или описание | Новая версия не создаётся |
| Есть запланированные рейсы | Переходят на новую версию: они ещё не выполнялись |
| Есть завершённые и выполняемые рейсы | Остаются на своей версии |

История версий видна в редакторе маршрута: когда создана, кем, что меняли, сколько рейсов
на каждой версии. Старые версии не удаляются, пока на них есть рейсы.

## Создание маршрута на карте

Маршрут собирается кликами по карте. Нажатие на пустое место создаёт новую остановку
(название вводится тут же), нажатие на серую точку добавляет существующую. Точки маршрута
показаны нумерованными маркерами в порядке движения, порядок меняется стрелками в списке.

Кнопка «Показать путь по дорогам» строит предпросмотр через сервис маршрутизации и предлагает
подставить время в пути, рассчитанное по фактическим расстояниям. Новые остановки создаются
в справочнике только при сохранении маршрута.

## Путь по дорогам

Маршрут на карте — это не прямые линии между остановками, а реальный путь по улицам.
Геометрия запрашивается у OSRM-совместимого сервиса и сохраняется в базе: один раз при
создании или изменении маршрута, никогда во время отрисовки страницы.

Адрес сервиса задаётся переменной `ROUTING_URL`. По умолчанию используется публичный
демо-сервер OSRM — он не даёт гарантий доступности, поэтому для продакшена поднимите свой.
Если сервис недоступен, маршрут сохраняется с прямыми линиями и помечается в списке маршрутов
как «прямые линии»; кнопка «Построить путь по дорогам» перестраивает геометрию позже.

Геометрия используется в трёх местах:

1. **Карты** во всех трёх приложениях рисуют настоящий путь.
2. **Время прибытия по GPS** считается по остатку пути вдоль дороги, а не по прямой до остановки.
3. **Отклонение от маршрута** измеряется от линии дороги, поэтому автобус на изгибе улицы
   больше не выглядит сошедшим с маршрута.

## Прогноз спроса

Раздел «Прогноз» показывает, сколько пассажиров ожидается на каждом запланированном рейсе
ближайшей недели. Метод намеренно простой и объяснимый: средневзвешенное число пассажиров
по сопоставимым прошлым рейсам, где свежие рейсы весят больше (период полураспада 14 дней).

Система сначала берёт этот же рейс в этот же день недели. Если таких рейсов меньше трёх,
она расширяет выборку: этот же рейс в другие дни, затем этот день недели, затем весь маршрут.
Использованная группа и число рейсов показываются рядом с каждым прогнозом, чтобы администратор
видел, на чём основана цифра.

| Риск | Условие |
|------|---------|
| Не хватит мест | Ожидаемое число пассажиров больше вместимости |
| Возможна нехватка | Максимум за период превышал вместимость |
| Низкая загрузка | Ожидается меньше 40% вместимости |

Для пиковых отправлений предлагается добавить рейс за 15 минут до пика — одной кнопкой.
Отдельная таблица показывает, кто именно не помещается: сотрудники, записавшиеся после того,
как места закончились.

## Рекомендации по маршрутам

Домашние адреса сотрудников группируются по близости. Для каждой группы считается расстояние
до ближайшей остановки. Группы дальше 600 метров пешком считаются неохваченными.

Дальше система предлагает самое дешёвое решение:

1. **Добавить остановку**, если группа живёт рядом с существующей линией.
2. **Создать маршрут**, если рядом нет ни одной линии. Группы в противоположных концах города
   получают отдельные маршруты: система не сводит их в один рейс.

Черновик маршрута создаётся одной кнопкой вместе с недостающими остановками, но со статусом
«черновик» — пассажиры его не видят, пока администратор не проверит и не активирует.

## Технологии

Next.js 16 (App Router, Server Actions), React 19, TypeScript, Tailwind CSS v4,
